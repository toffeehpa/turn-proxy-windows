# Архитектура

FreeTurn для Windows - тонкая оболочка над ядром. Сеть, DTLS, обфускация и капча живут в `freeturn-core.exe`. Схема как у OpenVPN GUI и его interactive service: трей `FreeTurn.exe` работает без прав, ядро запускает служба `FreeTurnService` от LocalSystem.

## Процессы

- **`FreeTurn.exe`**: трей, профили, `ConnectionManager`. Права обычного пользователя
- **`freeturn-service.exe`** (`FreeTurnService`): Named Pipe для трея и запуск ядра. LocalSystem, автозапуск
- **`freeturn-core.exe`**: ядро, дочерний процесс службы в Job Object, с `-routes`

Трей передаёт службе не командную строку, а профиль. Служба проверяет его тем же `validate()` и сама строит аргументы: процесс без прав не может подсунуть ядру от SYSTEM свои флаги. Ядро берётся только рядом со службой, из папки установки.

## Слои

- **`src/core`**: логика без Win32 API - профили, JSON, ссылки `freeturn://`, аргументы ядра, конечный автомат, `ConnectionManager`, разбор логов ядра. Её проверяют unit-тесты с Mock-движком
- **`src/win`**: Win32 - процесс ядра и Job Object (`ProcessEngine`), хост службы (`ServiceHost`), клиент службы (`ServiceEngine`), Named Pipe, DPAPI, пути, атомарная запись файлов
- **`src/service`**: обвязка SCM вокруг `ServiceHost`
- **`src/app`**: трей, меню, окна профиля и настроек, строки ru/en, `wWinMain`

Движок ничего не знает про окна: события он отдаёт в callback, а `App` переносит их на UI-поток через `PostMessage`. `ConnectionManager` работает с `IEngine` и не различает, запускает ядро служба или тест.

## Потоки

- **UI-поток**: одно скрытое окно, цикл сообщений, трей, `ConnectionManager`. Всё состояние меняется только здесь
- **Монитор ядра** (`std::jthread`): ждёт выхода процесса или запроса остановки
- **Чтение пайпа службы** (`std::jthread`): события ядра от службы
- **Сервер пайпа** (`std::jthread`): команды второго экземпляра

В службе - свой поток пайпа, монитор ядра и чтение его stdout/stderr.

Остановка рабочих потоков - через `stop_token`, без `TerminateThread`.

## Окна

- **Скрытое окно**: сообщения трея, таймеры, события движка. Обычное, не `HWND_MESSAGE` - иначе не придёт `TaskbarCreated` после перезапуска Проводника
- **Профиль / Импорт**: одно окно для ссылки, файла и ручной правки
- **Настройки**: подключение при запуске, переподключение, подробный лог, Experimental

Окна состояния и лога нет: состояние - в меню и подсказке иконки, лог открывается файлом. Тема окон - светлая или тёмная, как у приложений Windows; в режиме высокой контрастности окна не перекрашиваются.

## Состояния

```text
Disconnected -> Starting -> Connecting -> Connected
Connecting / Connected / Captcha -> Stopping -> Disconnected
Connecting / Connected / Captcha -> Reconnecting -> Starting
Connecting / Connected / Captcha -> Error
```

Полная таблица - `can_transition()` в `src/core/connection_state.cpp`. Переход вне таблицы отклоняется и пишется в лог как ошибка.

- **Переподключение**: только если сессия уже была подключена и ядро упало без фатальной ошибки. До 5 попыток, паузы 2, 4, 8, 16, 30 с
- **Ошибка конфига или проваленная капча**: сразу `Error`, повторы не помогут
- **Смена профиля во время подключения**: остановка текущего ядра, затем запуск нового
- **Устаревшие события**: у каждого запуска свой `SessionId`, хвост лога прошлого процесса игнорируется

## Служба

- **Пайп** `\\.\pipe\FreeTurnService`: SYSTEM и администраторы - полный доступ, интерактивные пользователи - чтение и запись сообщений, удалённые клиенты отклоняются, имя нельзя занять раньше службы (`FILE_FLAG_FIRST_PIPE_INSTANCE`)
- **Проверка службы**: трей отправляет профиль с ключами, только если владелец пайпа - LocalSystem
- **Сессия**: одно подключение пайпа - один запуск ядра. Трей закрыл пайп или упал - служба гасит ядро
- **Протокол**: JSON-сообщения пайпа, `start` с профилем и `stop`; обратно `output`, `exited`, `error`
- **Отладка**: `freeturn-service.exe --console` - тот же хост без SCM

## Ядро

- **Запуск**: `CreateProcessW` с `CREATE_SUSPENDED`, процесс помещается в Job Object и только потом продолжает работу. Наследуются ровно два хэндла - пайп вывода и `NUL` на вход
- **Job Object**: `KILL_ON_JOB_CLOSE` - если служба упадёт, ядро не останется висеть. `SILENT_BREAKAWAY_OK` - браузер для ручной капчи, который открывает ядро, не закрывается вместе с ним
- **Параметры**: только CLI-флаги, как в `internal/config/args.go` ядра: отличия от дефолтов плюс `-routes`. JSON-конфига у CLI ядра нет
- **Остановка**: Ctrl+Break в группу процесса ядра (Go видит его как SIGINT), ядро закрывает сессию за 5 с. Через 7 с - `TerminateJobObject`
- **Состояние**: машиночитаемого статуса у CLI нет, поэтому FreeTurn читает лог. UDP-потоки видны только с `-debug` (`Established DTLS connection` / `Closed DTLS connection`), TCP-сессии - по `connected (active: N)`. `[DEBUG]`-строки в файл лога не пишутся, пока не включён подробный лог

## Данные

Всё в `%LOCALAPPDATA%\FreeTurn`, реестр не используется:

- **`profiles\<id>.json`**: открытая часть профиля
- **`secure\<id>.bin`**: ключ обфускации, Client ID и ссылки на звонки под DPAPI
- **`settings.json`**: настройки
- **`logs\freeturn.log`**: лог с ротацией, секреты профиля маскируются
- **`updates\`**: зарезервировано под обновления

Служба пишет свой лог в `%ProgramData%\FreeTurn\logs\service.log`, рабочая папка ядра - `%ProgramData%\FreeTurn\core`.

Профили обнаруживаются перечислением `profiles\`: файл с битым JSON или нерасшифровываемым blob-ом показывается в уведомлении и пропускается. Запись - через временный файл, `FlushFileBuffers` и `MoveFileExW` с `MOVEFILE_WRITE_THROUGH`.

## Второй Экземпляр

- **Мьютекс** `Local\FreeTurn.SingleInstance.<SID>` - один FreeTurn на пользователя
- **Named Pipe** `\\.\pipe\FreeTurn-<SID>`: DACL только для своего пользователя и SYSTEM, `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`
- **Проверка сервера**: перед отправкой клиент сверяет SID процесса-владельца пайпа со своим - ссылка `freeturn://` может нести ключ
- **Протокол**: одна строка `FTIPC1 <команда> [аргумент]`, до 32 КБ; импорт не сохраняет профиль сам, а открывает окно импорта
